# MALU RTL 独立审查：第一轮（实现前的数学与协议）

审查角色：agent2。日期：2026-10-25。本文不修改 DUT，也不声称已审查尚未提供的代码。

本轮依据主 agent 的实现方案：共享一个无符号 53×53 乘法器；32-bit 单端口分段 superaccumulator；单个在途 dot+C 事务；`PROJECT_EXACT` 确定性数值 profile。目标是合法浮点组合的精确乘积、精确归约，再在目标格式一次编码；不是 Rubin 设备位级拟合或 Rubin 吞吐实现。

## 1. 进入代码审查前必须冻结的约束

1. 明确 `K_MAX`、支持的输入/输出/scale tuple、容器编码、舍入模式、特殊值与错误策略。格式字段独立不等于任意组合合法。
2. 明确 F64 属于哪个项目矩阵 profile。若支持 F64，不能仅以 F16/TF32 的指数范围配置累加器。
3. 禁止未知 Ti16 raw 模式；decoded-Ti16 输入作为项目协议，逐操作数检查 `−2047 ≤ x ≤ 2047`，不能默认为所有 S16 都合法。PTX 饱和字段 NA 不能被项目接口自动当成可选饱和。
4. 本轮建议的 exact 数值定义为：`S = C + Σ_i ((A_i × B_i) × sA_i × sB_i)`，有限数全程按精确二进制有理数处理，中间不量化。若某 tuple 的 PTX 对缩放顺序、范围或特殊值另有规定，需单独列合规边界，不能用 PROJECT_EXACT 覆盖该差异。
5. 记录整数输出的模回绕/饱和位置。不得因为累加器内部够宽，就忽略 S32 可见溢出行为。

## 2. 浮点 exact 累加器范围证明

令所有有限值表示为整数系数乘二的整数次幂，累加器 LSB 为 `2^B`。

### 2.1 F64 界（数学事实）

- 最小正 F64 次正规数是 `2^−1074`，两个这样的输入相乘为 `2^−2148`。因此支持所有有限 F64 乘积时，必须有 `B ≤ −2148`。
- 任意有限 F64 输入绝对值小于 `2^1024`，故有限乘积绝对值小于 `2^2048`。不能把超过 F64 最大值的有限数学乘积提前变成 Inf，否则会破坏后续抵消。
- 有限 F64 的 C 绝对值小于 `2^1024`；其他合法 C 格式的范围应分别证明不超过此界。
- 若所有合法乘积（含 scale）也满足绝对值 `<2^2048`，K 项和 C 的保守界为 `|S| < (K_MAX+1)×2^2048`。
- 取 `B=−2148` 后，存储整数 `S/2^B` 的保守有符号位宽为：

`W ≥ 4197 + ceil(log2(K_MAX+1))`。

该式为便于证明的充分条件，含符号与保守 C 余量，不追求最小位宽。实际存储按 32 取整：

`WORDS = ceil(W/32)`，`W_STORE = 32×WORDS`。

例如 `1 ≤ K_MAX ≤ 65535` 时，`W=4213` 足够，取 `W_STORE=4224`，共 132 个 32-bit word。不是所有 K_MAX 都需要不同 RAM 深度；应计算后取整，不凭经验写常量。

### 2.2 scale 与合法 tuple

上述 F64 界仅在 **F64 与 scale 不被非法组合** 时成立。若任意开放 F64×UE8M0×UE8M0，正负指数范围都会扩张，现有界不能继续使用。

对 PTX 允许的低精度块缩放组合，应逐 tuple 计算：

`B_tuple = min(lsb_exp_A + lsb_exp_B + lsb_exp_sA + lsb_exp_sB)`，

`H_tuple = upper_bound(log2(|A B sA sB|))`。

UE8M0 有限 scale 可提供很小/很大的二次幂，但低精度 A/B 范围较小。应在 elaboration 常量/设计表中证明它们仍落在 common B/H 内；不能仅凭 scale 是 8 位就忽略其指数。

有效数宽度也要逐 tuple 证明：未缩放 F64 需要 53×53→106 位；低精度 A/B 再乘两个带有效数的 scale 时，中间系数通常远小于 53 位，但必须写出最大系数位宽。**任何需要把 106-bit 中间结果重新送进 53-bit 操作数口的路径都必须拒绝或重新分解，不能静默截断。**

UE8M0 是指数型 scale，其编码 0 不等于数值 0。UE4M3/UE5M3 带有效数，不能只加指数。禁用 scale 时，其 payload（包括特殊编码）不得进入数学计算；是否仍检查控制字段由请求合法表明确。

## 3. 共享乘法与带符号操作

- 建议共享乘法器只做无符号幅值乘法，sign 独立处理。FP64 幅值有效数最大 `2^53−1`，完整结果为 106 位。
- SystemVerilog 的乘法表达式必须在明确的 106-bit 上下文中求值；不依赖隐式定宽、隐式 signed 转换或先截断再扩展。
- S8/S4/Ti16 decoded 的 abs 在充分扩展后执行，尤其检查最负整数。禁止在原 signed 宽度中直接求负再误当有符号正幅值。
- scale 的序列乘法、A×B 和整数乘法共享同一状态与暂存寄存器时，要为每个中间寄存器规定写入时机和最大有效位数。收到 backpressure 或新操作数时，不得覆盖尚未消费的乘积。
- 整数乘积按数学整数加入 exact 累加器时，S32 最终编码是另一个明确步骤。混合 signed/unsigned 只开放合法组合。

## 4. 单端口分段累加器高风险项

### 4.1 进位、借位与符号扩展

若采用全宽 two's-complement 累加：

- 正乘积加入可跨越很多 word 传播 carry；负乘积减去幅值可跨越很多 word 传播 borrow。不能把更新窗口限制为 106-bit 乘积覆盖的几个 word。
- 一个 106-bit 系数按任意 bit offset 放置，最多涉及 5 个初始 32-bit word；这不限制后续 carry/borrow 的传播距离。
- 减法用 33-bit 中间量判断 `acc_word < chunk+borrow`，避免 `0xffffffff + 1` 在 32 位中先溢出。加法同理保留第 33 位 carry。
- 对 operand 已用尽之后的高位，应继续正确处理 carry/borrow 或符号扩展，直到完成规定的全宽更新。允许“提前结束”时必须有证明。
- 按 32 取整的 padding 高位必须维持符号一致性；最终 sign 取最高存储位。数学范围证明用于排除真实全宽溢出，不能用“最后丢掉 carry”替代证明。

### 4.2 同步 RAM 与扫描

- 单端口同步 read-modify-write 至少要区分读地址提交、读数据到达、写回和下一地址。相邻状态复用地址寄存器尤其容易错一 word。
- 任何归约/最终扫描开始前，最后一个写回与传播必须完成。
- 负数取幅值、找最高非零位、取结果有效数与 guard/sticky 跨 word 边界时，要固定扫描方向和 RAM 延迟。不可读取尚未写完的 word。
- 最终 sticky 是所有被丢弃的 **幅值** 位的 OR；不能直接对负数 two's-complement 低位做同样处理。
- 清零应为顺序 CLEAR 状态或等价 RAM 友好方案。数组在异步 reset 分支中整片清零可能阻止目标 RAM 推断；但不能为了 RAM 推断留下上个事务的旧位。

## 5. 最终舍入与有符号零

`PROJECT_EXACT` 必须写出输出舍入模式，不以语言内置 real 转换代替。

独立参考方法：对 `X=abs(S)` 先按目标格式确定量化单位 `2^u`；求精确商 q 和余数 r。RN 使用 `2r` 与除数比较，平局按 q 的最低位判断偶数；RZ 不增；RP 仅正非整除增；RM 仅负非整除增。处理增量后规格化进位、正常/次正规边界与溢出。这个算法应在 Python 大整数/有理数参考中实现，**不复用 DUT 的 word 扫描或状态机**。

必须覆盖：

- 小于最小次正规量的一半、恰好一半、略大于一半；目标最小正常数边界；最大有限数边界；舍入导致尾数进位。
- 精确非零但舍入到零时，应保留数值符号。
- 精确 S=0 时，superaccumulator 本身不能保留零的输入符号。若保留有符号零，需独立状态记录“是否出现非零有限项”和“零项符号”。建议明确选择：精确抵消在 RM 输出 −0、其余模式 +0；全部输入项都是 −0 时保留 −0；混合 +0/−0 按所选规则处理。此为项目约定，不能无依据写成 tcgen05 位级保证。
- 若项目统一 exact-zero 为 +0，也可实现，但必须在 profile 中明确，不得一边承诺保留符号零一边丢弃状态。

## 6. NaN、Inf、zero 和 scale

- 分类先于有限路径。NaN 结果建议统一 canonical NaN，并固定优先级，不依赖输入到达顺序。
- 有限数学乘积即使超出目标格式，也不应在 exact 归约前标记 Inf。
- 真正的 Inf 项同号累加保留该 Inf；同时出现正负 Inf 为 NaN。`0×Inf`、包括 scale 为 0 的情况，应有明确 invalid→NaN 规则。
- NaN 与 0 组合不能通过“乘积为零早停”隐藏；但禁用 scale 的 NaN payload 不应污染结果。
- E4M3 没有 Inf，只有特定 NaN 编码；不能把 exponent 全 1 一律走 Inf 路径。FP6/FP4、UE4M3/UE5M3 的有限/保留编码需按已有格式来源解码。
- scale 的分类与符号规则独立于 A/B；无符号 scale 不代表其容器任意高位都可忽略。reserved/padding 位应明确检查或按布局定义忽略。
- 遇到特殊值后不能停止计数却继续接收下一事务的数据；仍需按协议消费/终止当前 K，并确保只产生一次完成。

## 7. 单事务协议与错误

- 仅在 valid&&ready 时锁存命令/操作数/计数。命令接受后，所有格式、K、舍入、scale 配置、C、tag 都锁存，不能继续读外部变化中的字段。
- 明确 K=0 是拒绝还是返回 C；两者都应有测试，不得等待不存在的 operand beat。
- operand 接收不得早于清零/C 初始化完成；最后一项的 writeback 完成前不能发结果。
- last 与计数矛盾、额外 beat、缺失 scale、越界 Ti16 decoded、非法 tuple 都要定义完成状态及当前事务如何结束。不能让残留 beat 被当作下一事务的首项。
- 单事务时，直到响应被接收都应拒绝下一请求，或提供明确独立响应缓冲；不能在 output stalled 时覆写数据/tag/status。
- 响应 valid=1&&ready=0 时，data/tag/status 全部稳定；完成必须恰好一次。
- reset 清空所有控制/特殊值/舍入/计数状态并取消旧事务，不允许 reset 后出现陈旧响应。RAM 未立即清零时必须先 CLEAR 才开放计算。
- A/B block 边界计数基于实际接受的逻辑元素，不基于周期。不同 offset 时在较早到达的边界更新相应 scale。若一次 beat 不允许跨块，必须拒绝或通过 ready/分拍保证，不能静默使用前一块 scale。

## 8. 独立验证建议（第二、三轮执行）

### 定向 arithmetic 向量

1. **全宽 borrow 可观测测试**：F64 dot 含 `1×1` 与 `−2^−1074×2^−1074`，C=0。精确值为 `1−2^−2148`；RN 输出 1，RZ 输出 nextdown(1)。tiny 负项的 borrow 必须越过约 67 个低位 word 才能影响可见定向舍入。交换项顺序结果应一致。
2. 对称测试 `−1 + 2^−2148`，RZ 应为朝零相邻 F64；检测负数幅值、sticky 与符号错误。
3. **中间超目标范围但最终抵消**：最大有限 F64 的正、负乘积匹配抵消，再加一个有限 C。PROJECT_EXACT 应得到 C，不能因有限乘积过大提前产生 Inf/NaN。
4. 相同指数、指数差跨 31/32/33、63/64/65 位；全 0xffffffff word 的连锁 carry；跨 word 的最高位/guard/sticky。
5. NaN、正负 Inf、+0/−0、真正次正规数；scale 为最小/最大/zero/NaN/禁用的组合。
6. scale16/32 运行时切换；A/B offset 不同；边界前后仅一项不同；同一块所有项共用 scale 与下一块 scale 不同。
7. 整数极值与 mixed signedness；Ti16 decoded ±2047 合法、±2048 及更大幅值非法；S32 极限附近的最终回绕/饱和位置。

### 独立随机与变形性质

- 使用 Python `Fraction` 或有理数值类解码原始格式，精确相乘/相加，再用独立整数商余数算法输出编码。避免 host float 先丢失精度；不复用 DUT 解码函数或其分段累加算法。
- 对有限输入随机生成 sign、指数边界与尾数边界，采用指数分层抽样，不能只生成接近 1 的均匀浮点数。随机种子与失败向量落盘。
- 不移动 scale 语义的前提下，置换项序、拆分/合并事务中的数学和、加入正负相同项、加入合法零项，应满足 PROJECT_EXACT 的对应不变性。可见输出的重新量化 C 不能用于证明跨事务精确累加等价。
- 随机 valid/ready、长时间输出反压、输入气泡、忙时变化无效 payload、各状态 reset；参考 scoreboard 只统计握手接受的事务/元素。
- 若两轮检查发现并修改 DUT，第三轮必须重跑受影响的 arithmetic 回归和协议回归，再检查综合资源。不能只重复同一组 happy-path 测试称为三轮独立验证。

## 9. 资源复用的验收边界

数学正确不等于资源已经共享。后续必须检查综合网表/统计，确认一个 53×53 乘法器与一个 RAM 读写通道；SV 中分时调用 `*` 或用函数封装，不自动保证只生成一个乘法器。移位、比较、取负、sticky 和舍入组合逻辑也需检查是否意外展开成 4224-bit 多路加法器。面积/吞吐/频率须由实际综合结果或明确工具限制报告，不能从 Rubin 产品比例反推本实现。

## 10. 第二轮：实际 RTL 只读实现审查（仿真前）

已读取 `malu_pkg.sv`、`malu_core.sv`、`malu_decode.sv`、`malu_round_pack.sv`。本节记录源代码审查结果，**不是仿真或综合通过记录**。审查者未修改 DUT。

### 10.1 与主 agent 已确认的能力边界

`cfg_status` 接受的无 scale 浮点 cross-format A/B 以及 BF16 C/D，是主 agent 明确授权的 **PROJECT_EXACT 项目扩展组合**，不是 tcgen05 native tuple validator。当前 `profile != PROJECT_EXACT` 一律返回 `STATUS_UNSUPPORTED`。因此“拒绝 native 请求”已通过控制结构阅读确认，但不得将该门禁宣传为“全部 PTX native 合法组合验证”。

TF32 使用低 13 位清零的项目载体；Ti16 使用独立 decoded 模式，raw 关闭并拒绝，均不是声称完成 implementation-defined 原生位编码。Scaled 请求要求 low-float A/B、同值 A/B scale 格式以及有限的 block/format 子集。以上需要正文与测试能力矩阵同步列明；root 与 agent4 已确认。

### 10.2 数学范围与局部宽度复核

- Full 模式使用 `B=−2148`、132×32=4224 位。k 是 16 位且拒绝 0，当前最大 65535，符合第 2 节保守证明。仅在出现任意 F64 A/B/C/D 时选 Full；F64 A/B 不允许 blockscale。
- Low 模式 `B=−300`、20×32=640 位。无 scale 的最小 F32 乘积是 `2^−298`；当前 scaled low-float 最低的 E5M2/UE8M0 组合不低于 `2^−286`。所有合法有限项均可整齐落在该量化网格中。
- Low 最大 scaled 乘积小于 `2^286`，最多 65535 项的幅值和小于约 `2^302`；无 scale F32 乘积小于 `2^256`。最高符号位对应指数 339，当前有效范围有充足余量。
- Integer 模式使用 64 位/B=0。Ti16 decoded 最坏乘积为 2047²，65535 项加 S32 C 仍小于 `2^39`；当前其他整数模式范围更小，64 位足够，54-bit `round_sig` 也足以承载最大整数幅值。
- 138-bit `term_window` 可容纳完整 106-bit coefficient 左移最多 31 位，初始跨至多 5 个 word；后续扫描不局限在该窗口，满足全宽传播需要。

### 10.3 源代码中目前未发现错误的关键结构

1. **减法与符号**：`~chunk + carry`、负项 carry 初值 1，且从 term_start 扫描至 active_words 末尾，等价于全宽 two's-complement 减法。窗口之外的 chunk=0 会继续以全 1 加数传播符号/借位。负整数 abs 通过同一个 word adder，未在原窄 signed 位宽中求负。
2. **同步 RAM**：ACC_READ/ACC_WRITE、ABS_READ/ABS_WRITE 及各扫描 READ/TEST 分开；最后写回之后才进入读取状态。数组不在 reset 分支中整体清零，新事务先顺序 CLEAR 再注入 C。
3. **特殊值**：PREPARE 对 NaN/Inf/zero/scale 做分类；每项分类标志在 NEXT_ITEM 决策前已有一个时钟更新。有限大乘积不提前被转换为目标格式 Inf，因此保留抵消能力。
4. **负零**：all-negative/all-positive zero 标志与非零有限项分开维护；精确抵消在 RDN 给 −0，其余模式 +0，全部 −0 按输入零符号保留。非零幅值舍入至零时 pack_sign 仍保留数值符号。
5. **GRS**：最终取幅值后 gather，guard/round 固定位置，sticky 对每个 word 的所有低位做 OR，未用多个 nonblocking 零写覆盖先前的 sticky=1。ROUND_LOW/ROUND_HIGH 复用加法器进行 54 位进位。
6. **编码**：subnormal→normal、round carry、定向溢出至 Inf 或最大有限值的分支，从位宽/指数公式阅读上自洽。NaN 输出采用正 canonical quiet NaN。
7. **S32 输出**：在完整数学整数归约之后做最终 saturate 或 modulo；负幅值先取低 32 位再补码，符合最终模 2^32 的计算。负向恰好 2^31 幅值不会误判为溢出。
8. **事务**：req/op 仅在各自 ready 状态接受；最后 beat 的每个 lane 处理完成后才发响应；RESPOND 停留期间没有覆盖 data/tag/status 的代码路径；reset 清除控制并使下一事务重新 CLEAR。

“未发现错误”仅描述审阅到的结构，不排除模拟调度、工具解释、格式表、极端输入或协议交错中的缺陷。

### 10.4 必须由实际测试/综合闭合的事项

- 运行第 8 节可观测 borrow、正负大乘积抵消、subnormal/RNE tie/有符号零、整数最终溢出等向量，并与独立 Fraction 参考比较。
- 检查不同 offset 的 scale cache：边界允许更新，块内不同 payload 拒绝，beat 跨最早 A/B 边界拒绝。计数必须只随实际 op 握手前进。
- 记录 malformed beat 后立即错误完成的协议：上游收到错误后丢弃该请求剩余数据，不能将残留数据无命令地送入后续事务。当前 DUT 不实现自动 drain 剩余 K。

### 11.3 协议测试不是空占位

已逐段读取 `tb_malu.sv` 的 `protocol_tests`、request/beat/response 驱动以及完成检查，核对：

## 12. 最终 delta：禁用 FP64 时同时窄化乘法器

最终 core 使用 `SHARED_MUL_W = ENABLE_FP64 ? 53 : 24`，无符号乘积为 `2*SHARED_MUL_W` 位，再零扩展至原有 106 位公共累加接口。所有现行 round1/2/3 报告源签名均已更新为 §11.1 的最终签名；独立 SHA 核对无差异，四份 run log 数量/周期不变。没有沿用旧版本报告替代新版本验证。

窄化安全依据：FP64 off 的合法无 scale 浮点 A/B 最大有效数为 F32 的 24 位；scale 模式只允许 low-float，A/B 原有效数最多 4 位、带有效数的 scale 最多 4 位，故每侧缩放后系数最多 8 位；UE8M0 系数为 1。整数 A/B 最大为 decoded Ti16 的 11 位幅值。S32 C 不经过乘法器。所有 F64 A/B/C/D 请求会被配置门禁拒绝。因此不存在合法 53 位系数被 24 位截断的问题。

已独立检查最新 elaboration XML：剥离无符号零扩展后乘数输入确为 53/53 或 24/24，乘法表达式结果类型确为 106/48 位，各配置单个非常量乘法节点；acc_ram 分别 132/20 个 32 位 word，共享 word 加法结果为 33 位。表达式按 SystemVerilog 规则可能显示到结果宽度的零扩展，不应把该包装误报为输入有效位宽。

资源清单脚本曾因优化器消去中间别名而抛 KeyError；按表达式 dtype 修正并重新完成 Round 3 后，当前 `resource_inventory.json` 与独立 XML 核对一致。这属于清单提取故障，不是将失败的 RTL 仿真写成通过。上述资源仍仅为 elaboration 结构证据，不是 PPA 或技术映射签核。
